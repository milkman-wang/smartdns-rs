# Rust 版在 OpenWrt 上能快多少？

## 结论先行

没有可信的公开数据能证明 SmartDNS-rs 比 SmartDNS C 在同一台 OpenWrt 设备、同一份规则和同一组上游下固定快多少。语言本身也不给 DNS 服务器一个固定倍数。对家用路由器，网络等待、TLS、测速策略、缓存命中率和规则规模通常比 Rust/C 的语法选择更重要。

下面是工程预期，不是本项目已测出的承诺值：

| 场景 | 预期差异 | 原因 |
| --- | --- | --- |
| 冷缓存、访问公网 UDP/DoH 上游 | 端到端延迟通常相差不到 1% | 10–100 ms 主要在网络、上游解析和测速 |
| 热缓存、小规则集 | 吞吐/CPU 大概率在 C 的 ±20% 内 | 两者都只做内存查找和 UDP I/O，C 可能更省指令 |
| 很多并发 DoT/DoH/DoQ 请求 | Rust/C 吞吐可先按约 0.9–1.5 倍做容量估算 | Tokio 的调度和连接复用有机会占优，但 rustls/ring 与 C 版 TLS 栈、设备加速能力可能让任一方领先 |
| 低内存、低端 MIPS/ARM | C 通常更合适 | Rust 静态依赖、TLS 和异步运行时带来更大的包体/RSS |

因此不能把“Rust 更安全”直接换算为“Rust 更快”。在没有目标设备 A/B 数据前，实际决策可理解为：公网查询延迟几乎不会因换语言而改善；CPU 饱和的加密并发场景才有出现约 10%–50% 吞吐提升的可能，同时也要接受约 10% 变慢的可能。本适配的主要收益是内存安全、类型化解析器、现代异步协议栈和更容易维护的并发代码。

## 公开数据能说明什么

[OxiDNS 2026-07 的同机基准](https://oxidns.org/benchmarks/)测到了 **C 版** SmartDNS Release 48.2：其 cache-hotpath 最大稳定点为约 78,354 QPS、P99 0.927 ms、进程 CPU 99.8%、RSS 6.3 MiB。它证明 C 版的热路径已经很高效，但该矩阵没有 SmartDNS-rs，所以不能据此算出 Rust/C 比值。

SmartDNS-rs 的仓库性能工作流只做 Rust 版本的回归检测，且运行在 GitHub x86 runner；它同样不是 OpenWrt 路由器上的 C/Rust A/B 测试。当前没有同时满足“同一设备、同一配置、同一负载、两个实现”的公开结果，因此上表只能作为立项估算范围。

## 公平实测方法

必须比较同一台设备上的 OpenWrt 包，不能拿 x86 桌面 Rust 数据对比路由器上的 C 包。建议至少记录：

1. 固件版本、CPU 型号/频率、架构、内存和两个包的精确版本；
2. 相同上游、缓存、TTL、双栈选择、测速模式和规则文件；
3. 固定 CPU governor，停止会影响结果的流量整形/统计任务；
4. 分开测热缓存、冷缓存 UDP、DoH/DoT 和大规则集；
5. 每组预热后重复至少 5 次，报告中位数和 P95/P99，而不是只报最好值；
6. 同时记录 QPS、延迟、CPU、RSS、包体积和丢包/超时。

可在另一台有线 LAN 主机上用 `dnsperf` 施压：

```sh
dnsperf -s ROUTER_LAN_IP -p 53 -d cached-queries.txt -l 30 -c 64 -Q 10000
```

路由器侧同时采集：

```sh
pidof smartdns
top -b -n 1
cat /proc/$(pidof smartdns)/status | grep -E 'VmRSS|VmHWM|Threads'
ls -lh /usr/sbin/smartdns
```

热缓存用一批已预查询的域名；冷缓存每轮使用新的、可控的权威域名，避免公共递归器的缓存污染。C 版和 Rust 版各自重启、预热并交替测试，避免温度和网络时段形成系统偏差。

## 如何判断值得替换

- 设备日常 DNS CPU 低于一个核心的 10%：延迟、稳定性和内存比极限 QPS 更有意义。
- 只有 64/128 MB 内存或 8/16 MB 闪存：先比较安装包、`VmRSS` 和启动峰值，C 版往往占优。
- 大量加密上游、客户端很多、并发突发明显：Rust 版最可能体现异步并发的价值。
- 需要严格结论：在目标路由器运行上面的 A/B 流程。本仓库现有 `contrib/perf` 只测试 SmartDNS-rs 自身场景，不能当作与 C 版的对照数据。
